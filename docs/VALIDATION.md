# 第一版验证记录

验证日期：2026-09-23。这里区分工程流程验证和模型质量评估，避免把模拟结果或小样本接口测试误当作生产基准。

## 数据与构建约定

- 160 条内置数据通过实际 API 的 Pydantic 数据模式校验。
- 行 ID 与文本均唯一；dev 96 条、test 64 条；四类总数各 40 条。
- 每个基础场景的四种格式变体只属于一个拆分；生成器输出可确定性复现。
- 数据按类别交错排列，前 12 条 test 样本四类各 3 条。
- 后端 73 项测试通过，覆盖调用、适配器、评分、任务状态及输入边界等行为；本地复现命令见 [README](../README.md#测试与可复现性)。持续集成会重复后端检查与前端构建。

## 容器交付验证

在 Docker Desktop 的 Linux ARM64 环境完成多阶段镜像构建：Node.js 22 + pnpm 10.17.1 构建前端，Python 3.12 运行后端。锁定依赖安装与前端类型检查/生产构建均通过。

- 容器使用非 root UID `10001`，可正常写入专用数据卷。
- 首页与编译后的 JS/CSS 资源返回成功。
- 开启平台访问密钥后，健康端点可用，未鉴权数据请求返回 401，鉴权后的模型、数据与指标接口可用。
- 首次运行初始化 2 个 Demo 服务及 160 条合成工单。
- 通过完整 HTTP 接口完成 32 次规则服务调用，并导出 Markdown / JSON / CSV 报告。
- 重启容器后，已完成实验与全部 32 条请求记录仍在。

这验证了本仓库的镜像与本地持久化流程。没有在此处宣称所有 CPU 架构、云平台或部署方式均经过实测。

## 全平台真实模型验证（主要证据）

使用平台 API 创建实验，调用同一个本地 `qwen2.5:0.5b` 模型的 Ollama 原生与 OpenAI 兼容接口，分别运行 test 分组前 16 条工单，四类各 4 条，总计 **32 次真实推理**。实验完成，报告由平台直接导出：

- [可读的 Markdown 报告](examples/real-integration-report.md)
- [完整配置与逐条结果 JSON](examples/real-integration-report.json)
- [逐条结果 CSV](examples/real-integration-report.csv)

| 协议 | 有效输出 | 字段精确匹配 | 类别匹配 | 宏平均 F1 |
| --- | ---: | ---: | ---: | ---: |
| Ollama 原生 | 16 / 16 | 114 / 128（89.06%） | 9 / 16（56.25%） | 0.5345 |
| OpenAI 兼容 | 16 / 16 | 114 / 128（89.06%） | 9 / 16（56.25%） | 0.5345 |

参数为 temperature 0、max_tokens 1024、timeout 60 秒、并发 1；两个协议按顺序执行。数据内容摘要为 `da82b3b9a0659cd7136679b3af032b799f2260dba1c87241883203b26c1a18ab`，对应应用对行内容规范化后的摘要，而非文件字节摘要。

这验证了平台真实调用、任务状态、存储、评分和报告导出链路，也保留了小模型的分类与字段错误。32 次调用对应 **16 个唯一样本、同一套权重、两个接口**，并不等于两个独立模型或 32 条独立测试样本。4 条输入含显式类别，其余 12 条没有；样本来自共享模板合成数据，并非生产数据。

模型在此实验前已经加载，部分样本用于此前接口调试；系统没有自动预热，也没有卸载并重置模型状态。报告包含实测延迟，但这一热模型、小样本、单次运行不能作为通用性能基准或设备选型结论。请结合逐条结果阅读，不能只引用有效输出率。

## 先前的适配器冒烟检查

已对同一个本地模型通过两种协议直接调用项目适配器，各执行 4 条合成工单。这验证了真实网络请求、结构化输出解析和评分衔接；**不是两个独立模型的对比，也不是完整 test 集评测**。

| 项目 | 实测配置 |
| --- | --- |
| 运行环境 | macOS 15.6.1 / Apple M4 / 16 GiB 内存 / Python 3.12.14 |
| 推理服务 | Ollama 0.34.3 |
| 模型 | `qwen2.5:0.5b`，GGUF，Q4_K_M |
| 权重摘要 | `a8b0c51577010a279d933d14c2a8ab4b268079d44c5c8830c0a93900f1827c67` |
| 提示词 | `manufacturing-extraction-v1.0` |
| 冒烟参数 | temperature 0、max_tokens 1024、timeout 120 秒、并发 1 |
| 样本 | `SYN-0013`、`SYN-0053`、`SYN-0093`、`SYN-0133` |
| 加载状态 | 已加载的热模型；这些样本此前用于接口调试 |

| 协议 | 完整有效输出 | 字段精确匹配 | 观察到的问题 |
| --- | ---: | ---: | --- |
| Ollama `/api/chat` + JSON Schema | 4 / 4 | 30 / 32 | 两条“未停机”被输出为 null，标准答案应为 0 |
| OpenAI-compatible `/v1/chat/completions` + JSON Schema | 4 / 4 | 30 / 32 | 同上 |

这 4 条输入都明确写出了类别，模型返回的类别与文本一致，因此这里不把类别匹配结果作为分类推理能力的证据。数据格式简单、样本极少、同一批输入曾用于调试；不能据此宣称特定准确率、性能优势或制造业适用性。公开验证以本页前述 32 次全平台调用及其原始报告为主要证据。

调试中发现宽松 JSON 输出模式不能稳定保证完整字段，最终兼容适配器使用 `response_format` 的 JSON Schema 且 `strict: true`。其他兼容服务仍需单独验证这一能力；系统不会自动回退或重试。

## 如何复现与扩展

1. 启动 Ollama，准备相同模型，并记录 `ollama list` / 服务模型详情中的权重信息。
2. 按[部署文档](DEPLOYMENT.md)分别登记 Ollama 原生和 OpenAI 兼容端点，确保两者指向同一权重。
3. 在工作台选择上述两个端点、test 分组、样本数 16、并发 1，复现主要实验；或者选择 64 条运行完整 test 集。前述四个 ID 只用于较窄的适配器检查。
4. 导出原始 JSON 与 Markdown 报告，保留模型、环境、数据哈希、样本选择和预热方式。
5. 若进行真实选型，另建经授权、独立整理并人工复核的保留测试集，依据[评测方法](EVALUATION.md)解释结果。

默认 `scripts/smoke_test.py` 使用规则演示模型，是无需 GPU 的工程检查，与本页真实模型接口验证分开。
