# 数据卡：制造业合成工单 v1

## 来源与用途

`data/manufacturing_tickets.json` 包含 160 条中文模板合成工单。40 个设备事件场景和对应标准答案由项目实现时设计，每个场景生成 4 种格式变体。没有使用企业工单、客户文档、个人信息或外部模型生成结果。

标准答案由生成器中的场景及字段规则直接构造，不通过读取 Demo 模型输出生成。这里的“人工设计”表示规则和场景是显式编写的，**不表示存在真实工程师标注、独立标注团队或双人审核**。该数据用于接口、评测、报告及故障流程验证，不是工业故障基准。

## 规模与拆分

| 类别 | dev | test | 合计 |
| --- | ---: | ---: | ---: |
| mechanical（机械） | 24 | 16 | 40 |
| electrical（电气） | 24 | 16 | 40 |
| software（软件） | 24 | 16 | 40 |
| other（其他） | 24 | 16 | 40 |
| 合计 | 96 | 64 | 160 |

同一基础场景的四个变体只属于一个拆分，dev 和 test 没有重复文本或重复场景。两个拆分仍然共享设备词汇、字段结构、书写模板和生成方法，因此 test 不是独立生产分布。数据按四类交错排序，小样本前缀也覆盖多类；评测系统按当前数据顺序选取前 N 条，不随机抽样。

每条记录包含 `id`、`text`、`expected` 和 `split`。`expected` 的全部 9 个字段必须出现，除 `category` 外都允许 `null`。

## 字段定义

| 字段 | 类型 | 标注约定 |
| --- | --- | --- |
| `equipment_id` | string / null | 工单明确给出的设备编号，与故障码分开 |
| `equipment` | string / null | 设备名称，如“贴标机” |
| `production_line` | string / null | 保留原文产线名称，如“3号产线” |
| `reported_at` | string / null | 有完整年月日时使用 `YYYY-MM-DD`，不推测缺失年份 |
| `fault_code` | string / null | 明确报告的故障码；“无故障码”记为 null |
| `category` | enum | mechanical / electrical / software / other |
| `symptom` | string / null | 对应“现象”的原文短语 |
| `action_taken` | string / null | 已执行措施的原文短语；未记录则为 null |
| `downtime_minutes` | integer / null | 非负整数分钟；明确未停机为 0，未知为 null |

类别按记录描述的主要问题分配：机械磨损、运动卡滞、密封泄漏归 mechanical；供电、传感器、控制电路归 electrical；软件程序、配置、通信服务归 software；耗材、清洁、交接、物料周转和无异常巡检归 other。它们是这个项目的评测标签，不是工业故障标准或维修建议。

## 覆盖情况

- 10 类设备名称，40 个基础场景，每类故障 10 个场景。
- 分号、换行、竖线、句号四种字段分隔格式，以及冒号/等号和字段顺序变化。
- 完整 ISO 日期与中文年月日，输出都使用完整 ISO 日期。
- 缺失字段同时采用省略和“未记录”；明确否定包含“无故障码”“未停机”。
- 设备编号空值 23 条，产线空值 15 条，报告日期空值 13 条，故障码空值 64 条，处理措施空值 18 条，停机时长空值 10 条；56 条明确未停机。
- 40 条（25%）含有显式类别标签，其余 120 条需要根据症状分类。显式类别会降低分类难度，评估时应理解这一点。

## 局限

1. 模板多样性远小于真实工单：没有 OCR 噪声、语音转写、方言、多事件长文本和附件。
2. 设备名称和现象在每条记录中都存在，没有覆盖这些字段缺失时的所有行为。
3. 四类均衡且相对清晰，真实业务可能类别失衡、多标签并存、原因未知。
4. 空值精确匹配可能提高总体字段分数；应检查非空及关键字段，不能只看平均值。
5. Demo 解析器与数据共享中文字段约定，高分不意味着真实自然语言泛化能力。
6. 没有评估根因分析、维修方案正确性、安全控制或现场可操作性。

## 复现与版本

在仓库根目录运行：

```bash
python scripts/generate_dataset.py
git diff --exit-code -- data/manufacturing_tickets.json
```

生成过程无随机数、网络请求或当前时间依赖。源文件修订号为 `1.0`；导入应用时保存行内容的规范 JSON SHA-256，用于实验追踪。这个摘要针对 `rows` 规范序列化结果，**不等于原 JSON 文件字节的 SHA-256**。运行数据库已存在的数据不会因修改源 JSON 自动替换；修订后通过导入创建新的数据集。

## 自带数据导入

可用「数据集」页面导入符合相同结构的 JSON，最多 1000 行、每行文本 8000 字符。自己整理的数据将 `source` 设为 `user`，保留 dev/test 拆分。每个拆分都应包含希望评估的类别。不要用 test 调提示词后继续称其为未见测试集；需要独立维护新的保留集。

```json
{
  "name": "我的工单测试集",
  "description": "经授权整理的示例",
  "source": "user",
  "revision": "1.0",
  "rows": [{
    "id": "ticket-001",
    "split": "test",
    "text": "设备：贴标机；现象：标签耗材用尽；停机时长：未停机",
    "expected": {
      "equipment_id": null,
      "equipment": "贴标机",
      "production_line": null,
      "reported_at": null,
      "fault_code": null,
      "category": "other",
      "symptom": "标签耗材用尽",
      "action_taken": null,
      "downtime_minutes": 0
    }
  }]
}
```
